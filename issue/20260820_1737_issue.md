# First Placement Test — "Terjadi kesalahan, coba lagi." saat submit/skip

Dilaporkan dari screenshot: akun sudah pernah placement test sebelumnya (level tersimpan `Explorer`), buka lagi layar First Placement Test (`/placement-test`), langsung muncul kotak pesan merah **"Terjadi kesalahan, coba lagi."** menggantikan konten yang seharusnya (intro/soal/hasil).

## Issue

`POST /api/placement-test` (baik submit jawaban maupun skip "Nanti Aja") dan `GET /api/me` gagal secara diam-diam di backend (`portal/`), dan client (`app/`) cuma bisa menampilkan pesan generik karena respons dari server tidak berbentuk JSON `{ error: "..." }` yang valid.

Direproduksi langsung lewat `curl` ke server yang sedang jalan di port 3000:

```
POST /api/placement-test  (jawaban asli, bukan skip)
→ HTTP 500 Internal Server Error
→ body KOSONG (bukan JSON)
```

```
GET /api/me
→ HTTP 200 OK, TAPI field baru (placementAttemptsUsed, placementAttemptsRemaining,
  latestPlacementResult) TIDAK ADA di respons — server masih menjalankan versi kode lama.
```

Di `app/src/account.ts`, `apiFetch()` menangani respons non-2xx seperti ini:

```ts
const message = typeof data.error === 'string' ? data.error : 'Terjadi kesalahan, coba lagi.';
```

Karena body 500 di atas kosong (`data` jadi `{}` setelah `res.json().catch(() => ({}))`), `data.error` bukan string → jatuh ke pesan fallback generik itu — persis yang muncul di screenshot.

## Root Cause

Proses Next.js yang jalan di port 3000 (PID sudah dicek lewat `ps`/`lsof`) adalah **`next-server` hasil `next start` (mode PRODUCTION)**, bukan `next dev`:

- `ps -p <pid> -o lstart,command` → nama proses `next-server (v16.3.1)`, mulai jam **12:54**.
- `portal/.next/BUILD_ID` bermtime **15:23** — build terakhir, tapi proses yang jalan **tidak pernah di-restart lagi setelah itu**.
- `portal/package.json`: `"start": "next start"` — mode ini menyajikan **snapshot hasil build**, bukan baca source langsung seperti `next dev`. Perubahan source setelahnya (schema Prisma baru — kolom `totalItems`/`attemptNumber`/`speakingSignals`, route handler `placement-test`/`me` yang diperbarui, `prisma generate` ulang) **tidak pernah masuk ke proses yang sedang berjalan**, betapa pun banyak file yang diedit setelahnya.

Akibatnya:
1. `GET /api/me` menjalankan versi lama `route.ts` → field baru tidak pernah dikirim ke client (dikonfirmasi lewat curl di atas).
2. `POST /api/placement-test` (submit asli) menjalankan `db.placementTestResult.create()` versi lama yang tidak menyertakan kolom `totalItems`/`attemptNumber` yang sekarang **NOT NULL** di skema — Prisma menolaknya, exception itu tidak tertangkap oleh route handler (tidak ada try/catch), Next.js membalas 500 kosong.

Ini BUKAN bug di logic `app.ts`/`placement.ts`/schema Prisma itu sendiri — semuanya sudah diverifikasi build bersih & migrasi jalan benar sebelumnya. ini murni proses server yang stale.

## Fundamental Solution

**Perbaikan segera** (bukan solusi mendasar, cuma buka blokir): matikan proses `next-server` di port 3000, jalankan ulang `npm run dev` di `portal/` (bukan `npm run start`) supaya kode & Prisma Client yang aktif selalu sinkron dengan source.

**Perbaikan mendasar — supaya kelas masalah ini tidak terulang**:

1. **Route handler API tidak boleh pernah membalas 500 kosong.** Semua route di `portal/app/api/**/route.ts` (`placement-test`, `me`, `auth/*`) tidak punya try/catch di level teratas — begitu ada exception tak terduga (mismatch skema Prisma, koneksi DB putus, dst), Next.js jatuh ke respons default yang tidak berbentuk JSON. Perbaikan: bungkus body tiap handler dengan try/catch yang selalu membalas `NextResponse.json({ error: '...' }, { status: 500 })` — supaya client SELALU dapat pesan yang bisa dijelaskan (dan devtools/log bisa menunjukkan exception aslinya), bukan cuma "Terjadi kesalahan, coba lagi." yang menyamarkan akar masalah apa pun bentuknya.
2. **`next start` sebaiknya tidak dipakai untuk pengembangan lokal sama sekali.** Konvensi yang jelas: `npm run dev` (mode dev, auto-reload) untuk kerja sehari-hari, `npm run build && npm run start` HANYA untuk mensimulasikan/menjalankan build produksi yang sudah final — dan kalau dipakai, harus di-restart eksplisit tiap kali ada perubahan source (tidak akan pernah auto-reload, sesuai desainnya). Ini perlu dicatat jelas di `portal/README.md` supaya tidak tertukar lagi di sesi berikutnya.
3. **Tanda staleness yang kelihatan.** Selama masih pakai `next start` di lokal, `GET /api/me` (atau endpoint kecil terpisah) bisa menyertakan `buildId`/timestamp build — supaya kalau versi yang jalan ketinggalan jauh dari source, itu langsung kelihatan dari respons API-nya sendiri, bukan baru ketahuan lewat gejala tidak langsung seperti pesan error generik ini.
